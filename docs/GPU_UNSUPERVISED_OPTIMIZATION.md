# GPU Unsupervised Optimization: On-Device Synthetic Data Generation

## Overview

This optimization moves the Breiman-Cutler synthetic data generation for unsupervised random forests entirely onto the GPU, eliminating redundant CPU work and PCIe transfers.

**Branch:** `optimize/unsupervised-gpu`

**Benchmark (MovieLens 25M — 59,047 movies, 23 features, 500 trees):**

| Version | Per Tree | Projected 500 Trees |
|---|---|---|
| Original (main branch, 1000 trees) | 1.254s | ~10.5 min |
| Bug (histogram disabled) | 154.96s | ~21 hours |
| **Optimized (this branch)** | **1.02s** | **~8.5 min** |

---

## Problem

Unsupervised RF works by classifying real samples (class 1) vs synthetic samples (class 0). Synthetic data is created by independently permuting each feature column (Fisher-Yates shuffle), destroying inter-feature correlations.

The old GPU path:

1. **CPU** builds expanded matrix `X_unsupervised_expanded_` (2n × mdim) with shuffled features
2. **CPU** runs `prepare_data()` — sorts 2n samples, computes ties, builds histogram bins
3. **H2D transfer** copies full 2n × mdim matrix to GPU
4. GPU grows trees using CPU-precomputed histogram bins

This meant 2× the PCIe bandwidth, O(2n log 2n) CPU sorting, and a large CPU-side allocation — all unnecessary since the GPU can do this work directly.

## Solution

### 1. GPU Synthetic Data Generation Kernel

**Files:** `cuda/rf_unsupervised_synthetic.cu`, `cuda/rf_unsupervised_synthetic.cuh`

A CUDA kernel generates synthetic data directly in GPU memory:

- **One block per feature** (e.g., 23 blocks for 23 features)
- Thread 0 of each block performs a Fisher-Yates shuffle using cuRAND
- Real data occupies rows `[0, n_real)` of `x_gpu` (already transferred)
- Kernel writes shuffled values into rows `[n_real, n_real + n_synthetic)`

```
x_gpu layout (row-major):
┌─────────────────────────┐
│ Real data (n_real rows)  │  ← copied from host (cudaMemcpy)
├─────────────────────────┤
│ Synthetic (n_syn rows)   │  ← generated by GPU kernel
└─────────────────────────┘
```

The kernel handles two cases:
- **n_synthetic >= n_real** (default, ratio=1.0): Copy real column to synthetic region, Fisher-Yates shuffle in-place, oversample with replacement if needed
- **n_synthetic < n_real**: Sample with replacement from real column using cuRAND

### 2. Half the PCIe Transfer

**File:** `cuda/rf_growtree.cu`

`gpu_growtree_batch()` now copies only real data to the GPU:

```cpp
size_t x_copy_bytes = generate_synthetic_on_gpu
    ? n_real * mdim * sizeof(real_t)      // NEW: half the data
    : nsample * mdim * sizeof(real_t);    // OLD: full 2n

cudaMemcpy(x_gpu, x, x_copy_bytes, cudaMemcpyHostToDevice);

if (generate_synthetic_on_gpu) {
    gpu_generate_synthetic_unsupervised(x_gpu, n_real, n_synthetic, mdim, seed, stream);
    cudaStreamSynchronize(stream);
}
```

### 3. Skip CPU `prepare_data()`

**File:** `src/rf_random_forest.cpp`

The GPU doesn't need CPU-sorted indices, ties, or CPU histogram bins. `prepare_data()` is skipped entirely for the GPU unsupervised path:

```cpp
if (!config_.use_gpu) {
    prepare_data();
}
```

GPU-native histograms (`gpu_compute_dense_bin_edges` + `gpu_bin_dense_data`) replace the CPU histogram computation, using only n_real samples for bin edges (synthetic has identical marginal distributions).

### 4. Real-Only Proximity

**Files:** `cuda/rf_proximity.cu`, `cuda/rf_proximity_upper_triangle.cu`

Proximity matrices are sized at n_real × n_real instead of 2n × 2n. All proximity kernels (FP16, INT8, NF4, RFGAP) filter to real samples only — synthetic samples exist for classification separation, not for measuring similarity.

`n_real_samples` is threaded through `RFConfig`, `RandomForestConfig`, and `GpuSparseForestConfig` to make it available to all kernels.

Leaf assignments still include all 2n samples (real + synthetic) for optional analysis.

## Bug Fix: Histogram Disabled on GPU Unsupervised Path

Skipping `prepare_data()` left `histogram_data_` as null, which caused `use_hist_gpu` to evaluate to `false`:

```cpp
// BUG: histogram_data_ is null when prepare_data() is skipped
bool use_hist_gpu = config_.use_histogram && histogram_data_ && histogram_data_->is_valid;
// → false, even though GPU-native histograms don't need CPU histogram data
```

This forced `gpu_growtree_batch` into the **presort fallback path**, which is catastrophic for large datasets:

1. **Presort**: `gpu_presort_features_kernel` — one block per feature, thread 0 only, **O(n²) insertion sort**. For n=118K, that's ~14 billion comparisons per feature. The comment in the kernel says "fast for n < 10,000" — unsupervised has 12× that.
2. **Split finding**: O(n) linear scan of sorted indices per node per candidate feature, vs O(bins≈256) with histograms.

There is no parallel sort fallback — the presort path was designed for tiny datasets only. The histogram path is the only viable option for large n.

Result: 155s/tree instead of 1s/tree (155× slowdown).

**Fix:** Recognize that GPU-native histograms are independent of CPU `histogram_data_`:

```cpp
bool have_cpu_hist = histogram_data_ && histogram_data_->is_valid;
bool use_hist_gpu = config_.use_histogram && (have_cpu_hist || config_.use_gpu);
```
